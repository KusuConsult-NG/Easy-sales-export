# Application audit — 2026-08-08

Prompted by three user complaints:

1. errors that were fixed keep breaking again
2. dashboard data is not correct
3. placeholders persist in the app

All three have identifiable causes. This document records what was verified, and
marks clearly where something is inferred rather than proven.

**Scope.** This covers the causes of those three complaints across the data
layer, the aggregation paths, and the onboarding/loan UI. It is not a
page-by-page review of all 204 pages. What is not covered is listed at the end.

---

## A. Introduced by the audit, not yet live — fix before deploying

### A1. The 5,000-row cap silently truncates repair scripts and broadcasts

Commit `99ed9fe3` ("perf(db): stop unlimited queries reading entire tables",
part of the 19 audit commits) added `DEFAULT_QUERY_LIMIT = 5000` to any query
with no `.limit()`. That is right for user-facing screens. It is wrong for
whole-collection sweeps, and several exist:

| Site | Was | Now |
|---|---|---|
| `data-recovery.ts:44` — `USERS.get()` | all users | first 5,000 |
| `schema-standardization.ts:43` — `USERS.get()` | all users | first 5,000 |
| `maintenance.ts:18` — `PROCESSED_PAYMENTS.get()` | all payments | first 5,000 |
| `sms-broadcast.ts:217` — `USERS.get()` | all users | first 5,000 |

With ~41,000 users, a repair script now processes **12% of them and reports
success**. An SMS broadcast reaches 5,000 people, not 41,000.

The adapter does log a truncation warning — but only once per collection per
process, and the caller receives a short array with no error. Nothing in the
return value says the work was partial.

**This is the best available explanation for complaint (1).** An admin runs a
repair, it reports done, and the same errors resurface for the ~36,000 users it
never touched. The fix looks applied and is not.

Before `99ed9fe3` these queries were unlimited: slow, but complete. The
performance fix converted "slow but correct" into "fast but silently partial".

**Fix:** whole-collection sweeps must paginate explicitly rather than inherit a
cap, and must fail loudly rather than return a truncated result. Nothing here has
reached production yet, so no data is affected.

## B. Wrong dashboard numbers — complaint (2)

### B1. Admin platform metrics are wrong in three separate ways

`src/app/actions/global-aggregation.ts` computes total revenue, transaction
count and user count.

**Revenue is the sum of at most 5,000 rows.** The query sets no `.limit()`, so
it inherits the cap above. A table cannot be totalled by fetching its rows.

**The correct count is fetched and thrown away.** A `.count()` query runs as
`usersSnap2` and is never referenced again. `totalTransactions` is taken from
`revenueSnap.value.docs.length` — the truncated array.

**Failures are reported as success.** It uses `Promise.allSettled`; if the
revenue query rejects, `totalRevenue` stays `0`, and the function returns
`success: true, error: null`. The dashboard displays ₦0 as though it were real.

### B2. Academy revenue has the same cap

`academy/_admin.ts:623` — platform-wide `PROCESSED_PAYMENTS` query, no `.limit()`.
Total course revenue is under-reported once there are more than 5,000 purchases.

### B3. Wallet balances can display a stale value

Covered in PR #13. A wallet holds its balance in both `wallets.balance` and
`wallets.raw_data->>'balance'`; reads prefer `raw_data`. Migrations 005/006
updated only the column, so a credit changed nothing the application could
show. Fixed by migration 011.

## C. Persistent placeholders — complaint (3)

### C1. The loan document upload step was never implemented

`src/components/loans/LoanWizard.tsx:376` renders this to users:

> "Document upload functionality - integrate with your file upload service"

That is a developer note displayed in production.

### C2. Every loan application carries a fake document

The same form defaults `documents` to:

```js
[{ name: "dummy_id.pdf", url: "https://example.com/dummy_id.pdf", type: "id" }]
```

`loanApplicationSchema` requires at least one document, and this default
satisfies it. With C1 there is no way to replace it, so **every business loan
application ever submitted references a document that does not exist**.

Worth checking what is actually stored on existing applications before relying
on any of them.

### C3. Terms and Privacy links go nowhere during onboarding

`marketplace/onboarding/steps/TermsStep.tsx:128,132` and
`export/onboarding/steps/TermsAcceptanceStep.tsx:112,160,186` link to `href="#"`.
Users are asked to accept terms they cannot open.

`/terms` and `/privacy` pages **already exist** — the links simply do not point
at them. A trivial fix with a compliance consequence on a financial product.

### C4. Profile falls back to placeholder identity

`src/app/profile/page.tsx:367` — when the session object is not populated the
page renders **"User Name"** and **"user@example.com"** rather than a loading or
error state.

## D. Why fixes keep regressing — the structural answer

Complaint (1) is not mainly caused by any single defect. Four things make
regressions likely and hard to notice.

### D1. No test exercises the real database

`jest.setup.js:104` mocks `@/lib/supabase-db` **globally**. All 390 tests run
against a hand-written fake. Nothing verifies real query semantics, the
`raw_data`/native column split, sentinel resolution, or the truncation cap.

This is not theoretical: B3 was written, reviewed, tested green, and verified on
staging — and was still broken, because every check ran on the same side of the
mock.

### D2. Type checking is disabled where it would help

`tsconfig.json` sets `"strict": true`, then immediately turns off the two flags
that catch this class of error:

```json
"noImplicitAny": false,
"strictNullChecks": false,
```

With 2,000+ untyped values, a refactor that breaks a caller compiles cleanly.

### D3. Fixes are applied per-site, not per-cause

The same defect shape recurs across the codebase — 44 files still use the
non-transactional `runTransaction`, and `FieldValue.increment` was
non-atomic at 142 call sites. Fixing one instance looks complete and leaves the
rest, so the same bug returns wearing a different screen's name.

`FieldValue.increment` is the clearest example: one adapter change fixed all 142
sites, where a per-site approach would have been 142 opportunities to miss one.

### D4. Repair scripts under-cover, so old bugs return

See A1. A data-repair sweep that silently processes 12% of users guarantees the
symptom comes back for everyone else, which reads exactly like a fix that did
not hold.

## What this audit did not cover

Stated so nobody assumes more was checked than was:

- No page-by-page review of all 204 pages across the nine modules
- No review of Farm Nation, WAVE or Export business logic beyond payment paths
- No verification against production data — every finding is from source
- No security review beyond the RLS work already done
- Notification, chat and review subsystems were not examined
- Accessibility and mobile layout were not examined

## Suggested order

1. **A1** — before anything deploys, or repair tools and broadcasts silently
   under-cover.
2. **C3** — one-line fix, compliance consequence, do it now.
3. **B1** — the dashboard numbers people are complaining about.
4. **C1/C2** — the loan product cannot collect documents; decide what to do
   about applications already holding a fake one.
5. **D1** — one integration test against real Postgres would have caught B3.
   The staging project now exists, so this is finally possible.
6. **D2** — enabling `strictNullChecks` is large, and is what stops the next
   two dozen of these.
